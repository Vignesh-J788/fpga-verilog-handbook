Debugging, Reports & Common Errors

Every engineer, at every level, spends more time debugging than writing new code. This chapter turns Vivado's reports and error messages from intimidating walls of text into a systematic, learnable skill.

📖 Intermediate Level🕐 —🧩 6 sections

Reading the Utilization Report

After synthesis or implementation (Chapter 24), the Utilization report breaks down exactly which chip resources (Chapter 7) your design consumes:

ResourceWhat it means if it's unexpectedly high
LUTsYour combinational logic is larger than expected — check for unsimplified Boolean expressions (Chapters 2–3) or accidentally duplicated logic.
Flip-Flops (FFs)More memory elements than expected — check for unintentionally-inferred latches (Chapter 11), or registers you meant to remove.
DSP slicesConsumed by multiplication/arithmetic (Chapter 7); unexpectedly high usage often means unnecessary multiplies in your design.
Block RAM (BRAM)Consumed by large memory arrays; watch for accidentally oversized arrays.
I/OPhysical pins used — this is hard-capped by your chip package, unlike the other resources.

A utilization report near or over 100% for any resource means your design simply won't fit on the target chip — the fix is either a smaller/more efficient design, or a bigger chip.

Reading the Timing Report

Chapter 13 introduced setup time, hold time, and the critical path conceptually — Vivado's Timing Summary report turns these into concrete numbers for your actual design:

  • WNS (Worst Negative Slack) — the tightest margin anywhere in your design between how much time a path needed and how much it had. A positive WNS means every path met timing; a negative WNS means at least one path was too slow for your declared clock frequency.
  • WHS (Worst Hold Slack) — the equivalent check for hold-time violations (Chapter 13), usually caused by paths that are too fast rather than too slow.
  • The failing path detail — clicking into a specific failing path shows its exact source, destination, and every delay contributing to it, letting you pinpoint precisely which piece of logic is the bottleneck.
Practical fixes for a negative WNS
In order of how often they actually help: (1) simplify or restructure the offending combinational logic to shorten its path, (2) add an extra pipeline register (an additional flip-flop stage) to break one long path into two shorter ones, or (3) as a last resort, lower your declared clock frequency in the XDC file if the design's actual use case allows it.

Common Error & Warning Messages, Explained

Message (paraphrased)What it actually meansTypical fix
Multiple drivers on netTwo separate assign statements or always blocks are both trying to drive the same wire — Verilog hardware can't have two things fighting to set one signal's value.Ensure exactly one assign/always block drives each signal; combine logic into one block if needed.
Latch inferred for signalAn always block doesn't assign a signal in every possible branch (Chapter 11), so the tool inserted a latch to "remember" its last value.Add a default assignment before the case/if, or an explicit default/else branch.
Port has no load / unconnected portAn output port is declared but nothing outside the module reads it, or an input port is declared but never actually driven.Check for a typo in the instantiation's port connections, or genuinely unused ports that should be removed.
Width mismatchA signal of one bit-width is connected to a port or expression of a different width — Verilog will often silently truncate or zero-extend rather than erroring, which can hide real bugs.Explicitly match widths, or intentionally slice/extend with a clear comment explaining why.
Combinational loopA combinational signal's logic path eventually feeds back into its own input with no clocked element breaking the cycle — an unstable, oscillating circuit.Insert a register (flip-flop) to break the cycle, or restructure the logic so it isn't self-referential.
Clock not found / unconstrained clockA clock signal exists in your design but has no matching create_clock constraint in the XDC file, so Vivado can't properly analyze its timing.Add a create_clock constraint (Chapter 24) for every actual clock signal in the design.

When Simulation Isn't Enough: The Integrated Logic Analyzer (ILA)

Simulation (Chapter 12) catches most bugs, but some problems only appear on real hardware — genuine electrical noise, mechanical button bounce, or subtle timing effects a simulator's idealized model doesn't capture. For these cases, Vivado provides the Integrated Logic Analyzer (ILA): a debug core you insert directly into your design, which captures real internal signals, in real time, while your FPGA is actually running — effectively giving you a waveform viewer plugged into the live chip.

The general idea (exact steps vary by Vivado version)
You mark the internal signals you want visibility into (often using a mark_debug attribute directly in your Verilog, or through Vivado's Set Up Debug wizard), re-run implementation so the debug core gets built into your bitstream, then use Hardware Manager to trigger captures and view live waveforms of your board's actual internal behavior — the real-world equivalent of everything you've practiced with $monitor and .vcd files since Chapter 12.

A Systematic Debugging Checklist

  1. Does it fail in simulation, or only on real hardware? If simulation already fails, the bug is a logic error you can find without ever touching real hardware.
  2. Re-check the truth table / expected output you derived by hand (Chapters 2–4) against the simulated waveform, line by line.
  3. Search the synthesis log for latch inferred or multiple driver warnings — these are almost always real bugs, not noise, even when the design "seems to work."
  4. If it passes simulation but fails on hardware, check the Timing Summary first — a design that's logically correct but violates timing can still misbehave physically.
  5. If timing is clean and it still fails on hardware, reach for the ILA to observe the real, physical signal behavior directly.

Summary

The Utilization report reveals whether your design fits the chip; the Timing Summary (WNS/WHS) reveals whether it runs fast enough. Most Vivado error messages map directly onto concepts already covered — multiple drivers, inferred latches, width mismatches, combinational loops, and unconstrained clocks are all mechanically explainable, not mysterious. When a bug only appears on real hardware, the ILA extends the same waveform-based debugging philosophy from Chapter 12 onto the live, physical chip.

Interview Questions

  • What does a "multiple drivers" error mean, and how do you fix it?
    It means two separate pieces of logic (e.g., two assign statements or always blocks) are both trying to drive the same signal, which is not physically valid. The fix is ensuring exactly one source drives each signal, consolidating logic into a single block if necessary.
  • What is the difference between a timing failure caught in simulation versus one caught after implementation?
    Simulation generally doesn't model real physical delays and won't reveal timing failures at all — Chapter 12's testbenches check logical correctness, not speed. Timing failures only appear after implementation, once the design has been placed and routed onto real chip resources with real physical delays.
  • When would you use an ILA instead of relying on simulation?
    When a bug only manifests on real hardware — due to physical effects like electrical noise, mechanical switch bounce, or hardware-specific timing interactions — that an idealized simulator cannot reproduce, requiring direct observation of live signals on the actual chip.

Viva Questions

  • What does WNS stand for?
    Worst Negative Slack.
  • What typically causes a "latch inferred" warning?
    An always block that doesn't assign a signal in every possible branch, forcing the tool to preserve its previous value with an unintended latch.
  • What does ILA stand for?
    Integrated Logic Analyzer.
