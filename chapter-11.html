A Quick Note Before We Start: Multi-Bit Buses

Every example so far used single wires. Real designs constantly need groups of bits — a "bus." You declare one using square brackets: wire [3:0] data declares a 4-bit bus named data, with bit 3 as the most significant bit (MSB) and bit 0 as the least significant bit (LSB) — exactly the place-value idea from Chapter 1's binary numbers. We'll use buses freely from here on.

if / else Inside always Blocks

Just like C, Verilog's if/else makes a decision — but remember, it must live inside a procedural block (always or initial), never on its own at the top level. When you chain several else if conditions, Verilog checks them in order, top to bottom, and stops at the first true one — this is exactly the "priority" behavior behind a priority encoder (Chapter 4, fully built in Chapter 18).

verilog · priority if/else chain
always @(*) begin
    if (req[3])
        grant = 2'b11;      // req[3] checked FIRST — highest priority
    else if (req[2])
        grant = 2'b10;
    else if (req[1])
        grant = 2'b01;
    else
        grant = 2'b00;    // fallback / lowest priority
end

The case Statement — A Cleaner Multi-Way Choice

When you're choosing between several fixed values of one signal (rather than several unrelated conditions), case reads far more cleanly than a long if/else if chain. Here's a tiny 4-function ALU (arithmetic logic unit) — a preview of Chapter 23's calculator project — choosing its operation based on a 2-bit opcode:

mini_alu.v
module mini_alu (
    input  wire [1:0] op,
    input  wire [3:0] a,
    input  wire [3:0] b,
    output reg  [3:0] result
);

    always @(*) begin
        case (op)
            2'b00: result = a + b;   // add
            2'b01: result = a - b;   // subtract
            2'b10: result = a & b;   // bitwise AND
            2'b11: result = a | b;   // bitwise OR
            default: result = 4'b0000;
        endcase
    end

endmodule
Never skip the default case
Omitting default means the tool has no idea what result should be for an uncovered case — and to "remember" the previous value in that situation, it's forced to insert an unintended latch (Chapter 5) into your design. This is one of the most common accidental-latch bugs in real Verilog code. Always include a default, even if it just holds a safe value like all-zeros.

Two close relatives are worth knowing: casez treats z/don't-care bits (written ?) as wildcards, and casex treats both x and z as wildcards — both are exactly the "don't care" idea from Chapter 3's Karnaugh maps, and they're the natural way to write a priority encoder's case list cleanly (Chapter 18).

for Loops

Verilog's for loop looks almost identical to C's, but remember: it lives inside a procedural block, and it doesn't "take time" on real hardware — it's simply a compact way of writing out repetitive logic (or repetitive testbench stimulus), which gets fully expanded before the circuit is built.

verilog · for loop example — counting set bits
integer i;
always @(*) begin
    count = 0;
    for (i = 0; i < 8; i = i + 1) begin
        if (data[i])
            count = count + 1;   // tally how many bits of data are 1
    end
end

Quick Detour: Using One Module Inside Another

Before we can build our capstone example, we need one more small piece of syntax: how to place (instantiate) one module inside another, connecting its ports to signals in the parent module. This uses named port connection, which is clearer and safer than position-based connection:

verilog · instantiating a module
full_adder fa0 (
    .a(A[0]),
    .b(B[0]),
    .cin(carry[0]),
    .sum(Sum[0]),
    .cout(carry[1])
);

Reading this out loud: "Place a full_adder, name this particular copy fa0, and wire its port a to my signal A[0], its port b to my signal B[0]," and so on. We'll cover this style of design (called structural modeling) fully in Chapter 14 — for now, you have exactly enough to follow the capstone below.

The Capstone: parameter + generate Build a Real N-bit Adder

Recall Chapter 4's ripple-carry adder — a chain of full adders, each one's carry-out feeding the next one's carry-in. Writing out four, eight, or thirty-two full adder instances by hand would be tedious and error-prone. generate loops let the tool build that chain automatically, for any width you choose, using a parameter.

Step 1 — A Reusable Full Adder (from Chapter 4's equations)

full_adder.v
module full_adder (
    input  wire a,
    input  wire b,
    input  wire cin,
    output wire sum,
    output wire cout
);
    assign sum  = a ^ b ^ cin;
    assign cout = (a & b) | (b & cin) | (a & cin);
endmodule

Step 2 — parameter: Making the Width Configurable

A parameter is a named constant that a module's user can override when instantiating it — perfect for "how many bits wide should this be?" questions.

verilog · declaring a parameter
parameter N = 4;   // default width, can be overridden by whoever instantiates this module

Step 3 — generate: Building N Full Adders Automatically

ripple_adder.v — works for ANY width N
module ripple_adder #(
    parameter N = 4
) (
    input  wire [N-1:0] A,
    input  wire [N-1:0] B,
    input  wire       Cin,
    output wire [N-1:0] Sum,
    output wire       Cout
);

    wire [N:0] carry;
    assign carry[0] = Cin;
    assign Cout     = carry[N];

    genvar i;
    generate
        for (i = 0; i < N; i = i + 1) begin : adder_stage
            full_adder fa (
                .a(A[i]),
                .b(B[i]),
                .cin(carry[i]),
                .sum(Sum[i]),
                .cout(carry[i+1])
            );
        end
    endgenerate

endmodule
What just happened
This one piece of code can build a 4-bit adder, a 16-bit adder, or a 64-bit adder — just by instantiating it with a different N — without writing a single extra line. The carry bus threads carry[i] into stage i's cin and takes carry[i+1] from its cout, exactly reproducing Chapter 4's ripple-carry diagram, generated automatically for any width.

To instantiate this with an 8-bit width elsewhere, you'd write:

verilog · overriding a parameter at instantiation
ripple_adder #(.N(8)) my_adder (
    .A(busA), .B(busB), .Cin(1'b0),
    .Sum(busSum), .Cout(busCout)
);

One more small tool worth knowing: localparam declares a constant exactly like parameter, except it can never be overridden from outside — useful for internal constants that must never change (like a fixed state-machine encoding in Chapter 22).

Summary

if/else chains check conditions in strict priority order; case statements cleanly select among fixed values of one signal (always include a default to avoid accidental latches). for loops repeat logic compactly inside procedural blocks. parameter lets a module's width or behavior be configured by whoever instantiates it; generate loops use that parameter to automatically build a repeated hardware structure — as shown by turning Chapter 4's single full adder into a genuinely any-width ripple-carry adder with just a few lines of code.

Key Points

  • if/else if chains = priority order, checked top to bottom.
  • case statements always need a default to avoid unintended latches.
  • casez/casex support don't-care (wildcard) matching.
  • parameter = configurable constant; localparam = fixed, non-overridable constant.
  • generate + genvar build repeated hardware structures automatically at compile time.
Memory Trick: "if/else checks in order, like asking questions one by one. case is a menu — pick your dish. generate is a photocopier — one full_adder becomes N of them, instantly."

Interview Questions

  • Why does an incomplete case statement risk creating an unintended latch?
    If some input combination isn't covered, the synthesis tool must preserve the signal's previous value for that case, which requires memory — an unintended latch — since the design didn't specify what should happen otherwise.
  • What is the purpose of a generate block?
    It lets you programmatically create repeated hardware structures (like N instances of a module) at compile time, based on a loop variable (genvar), rather than manually writing out each instance by hand.
  • How does a parameter differ from a normal variable in Verilog?
    A parameter is a compile-time constant that configures a module's structure (like bus width) and can be overridden by the instantiating module — it has no runtime existence in the hardware itself, unlike a signal.

Viva Questions

  • In an if/else if chain, which condition is checked first?
    The first one listed — conditions are checked strictly top to bottom, in priority order.
  • What keyword declares the loop variable used inside a generate block?
    genvar.
  • Can a localparam be overridden from outside its module?
    No — unlike parameter, localparam values are fixed and cannot be overridden at instantiation.

Reveal Answers to Practice Questions
1) Without a default, the tool doesn't know what value to hold for unlisted cases, forcing it to insert memory (a latch) to preserve the last value — almost always an unintended, buggy result.
2) It uses the default value declared in the parameter statement (N = 4), building a standard 4-bit adder.
3) Both styles work identically in simulation; if/else if can feel more natural for a small number of conditions, while case scales more cleanly and readably as the number of options grows.
4) parameter can be overridden by the module that instantiates it (e.g., #(.N(8))); localparam is fixed internally and can never be overridden from outside.
