Complete Code: All 7 Gates in One Verified Module

Rather than writing seven nearly-identical tiny files, real engineers often group closely related small gates into one module when they share the same inputs — here's all seven gates, sharing inputs a and b, written in clean dataflow style:

all_gates.v
module all_gates (
    input  wire a,
    input  wire b,
    output wire y_and,
    output wire y_or,
    output wire y_not_a,
    output wire y_nand,
    output wire y_nor,
    output wire y_xor,
    output wire y_xnor
);

    assign y_and   = a & b;
    assign y_or    = a | b;
    assign y_not_a = ~a;
    assign y_nand  = ~(a & b);
    assign y_nor   = ~(a | b);
    assign y_xor   = a ^ b;
    assign y_xnor  = ~(a ^ b);

endmodule

Behaviorally identical version: wrap the same seven lines in always @(*) begin ... end, changing = to keep blocking assignment and declaring every output as reg instead of wire (Chapter 14). Both produce exactly the same synthesized hardware.

Full Testbench — Verifying All 7 Gates At Once

all_gates_tb.v
module all_gates_tb;

    reg  a, b;
    wire y_and, y_or, y_not_a, y_nand, y_nor, y_xor, y_xnor;

    all_gates uut (
        .a(a), .b(b),
        .y_and(y_and), .y_or(y_or), .y_not_a(y_not_a),
        .y_nand(y_nand), .y_nor(y_nor),
        .y_xor(y_xor), .y_xnor(y_xnor)
    );

    initial begin
        $dumpfile("all_gates.vcd");
        $dumpvars(0, all_gates_tb);

        a=0; b=0; #10;
        a=0; b=1; #10;
        a=1; b=0; #10;
        a=1; b=1; #10;

        $finish;
    end

    initial
        $monitor("t=%0t a=%b b=%b | AND=%b OR=%b NOT_A=%b NAND=%b NOR=%b XOR=%b XNOR=%b",
                 $time, a, b, y_and, y_or, y_not_a, y_nand, y_nor, y_xor, y_xnor);

endmodule

Reading the Waveform

Common Mistakes Beginners Make

  • Confusing & and && (Chapter 10) — bitwise vs logical AND give very different results on multi-bit signals.
  • Forgetting endmodule — every module must close, or later code gets swallowed into it, causing confusing errors.
  • Mismatched port widths — connecting a 1-bit port to a multi-bit signal without realizing it, silently truncating or zero-extending.
  • Declaring outputs as wire in a behavioral (always) version — remember, anything assigned inside an always block must be reg (Chapter 9).
  • Typos in port names during instantiation — named port connections (.a(a)) silently fail to connect if the port name doesn't exactly match the module's declared port name.

Summary

All seven basic gates can be written cleanly in one small dataflow module, sharing common inputs where sensible. A single, well-structured testbench can verify all of them simultaneously by sweeping through every input combination and comparing against hand-derived expected values — the exact workflow you'll repeat for every remaining circuit in Part 5.

Memory Trick: "One testbench, every gate, every case — if your waveform doesn't match Chapter 2's truth table exactly, trust the truth table, not the code."

Interview Questions

  • Why might a designer group several small, related gates into one module?
    When they share the same inputs and serve a closely related purpose, grouping them keeps the code compact and readable, and makes verification (one shared testbench) simpler than managing many nearly-identical tiny files.
  • How would you verify that a NAND gate's Verilog implementation is correct?
    Write a testbench applying all 4 possible input combinations, and compare the simulated output at each combination against the NAND truth table (only 0 when both inputs are 1, otherwise 1).

Viva Questions

  • Write the dataflow Verilog line for an XNOR gate.
    assign y = ~(a ^ b); (or assign y = a ~^ b;)
  • How many input combinations must a 2-input gate testbench cover for complete verification?
    4 (00, 01, 10, 11).
