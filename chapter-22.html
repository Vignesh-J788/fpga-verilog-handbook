Project 1: LED Blinker (Clock Divider)

Here's a problem you'd hit immediately on real hardware: an FPGA's clock typically runs in the tens or hundreds of MHz — far too fast for a human eye to see any blinking at all. To make an LED visibly blink, you must first build a clock divider: a counter (Chapter 21) that only toggles the LED once every many thousands (or millions) of real clock cycles.

led_blinker.v
module led_blinker #(
    parameter DIVISOR = 4   // small value for simulation; real hardware uses millions
) (
    input  wire clk, rst,
    output reg  led
);
    reg [31:0] count;

    always @(posedge clk or posedge rst) begin
        if (rst) begin
            count <= 0;
            led   <= 0;
        end else if (count == DIVISOR - 1) begin
            count <= 0;
            led   <= ~led;   // toggle only once every DIVISOR cycles
        end else begin
            count <= count + 1;
        end
    end
endmodule
Real-world sizing
For a genuine ~1 Hz blink from a 50 MHz board clock, you'd set DIVISOR = 25_000_000 (toggling every half-second gives a 1-second full on/off cycle). Simulating 25 million clock edges would be painfully slow, which is exactly why the code above uses a tiny DIVISOR for testbenches — always parameterize this value so simulation and real hardware can use very different numbers.

Project 2: Traffic Light — Chapter 5's FSM, Delivered

Recall Chapter 5's promise: state + clock + transition rules = a Finite State Machine. A traffic light is always in exactly one of three states, moving to the next one after a timer expires.

This is written using the standard two-always-block FSM pattern: one clocked block updates the state (and its timer); a separate combinational block decodes the current state into actual output signals.

traffic_light.v
module traffic_light (
    input  wire clk, rst,
    output reg  red, yellow, green
);
    localparam RED = 2'b00, GREEN = 2'b01, YELLOW = 2'b10;

    reg [1:0] state;
    reg [3:0] timer;

    // Block 1: state register + timer (sequential)
    always @(posedge clk or posedge rst) begin
        if (rst) begin
            state <= RED;
            timer <= 0;
        end else begin
            case (state)
                RED: if (timer == 4'd7)  begin state <= GREEN;  timer <= 0; end
                     else timer <= timer + 1;
                GREEN: if (timer == 4'd7)  begin state <= YELLOW; timer <= 0; end
                     else timer <= timer + 1;
                YELLOW: if (timer == 4'd2) begin state <= RED;    timer <= 0; end
                     else timer <= timer + 1;
                default: state <= RED;
            endcase
        end
    end

    // Block 2: output decode (pure combinational, Chapter 4 style)
    always @(*) begin
        red    = (state == RED);
        yellow = (state == YELLOW);
        green  = (state == GREEN);
    end
endmodule
Why split into two always blocks?
This is the industry-standard FSM style: the sequential block only handles state changes (clean, non-blocking, easy to reason about timing for), while the combinational block only decodes state into outputs (using blocking assignment, since it has no memory of its own — Chapter 13's rules, applied to a real FSM). Keeping these concerns separated makes FSMs dramatically easier to debug and modify.
traffic_light_tb.v
module traffic_light_tb;
    reg clk = 0, rst = 1;
    wire red, yellow, green;

    traffic_light uut (.clk(clk), .rst(rst), .red(red), .yellow(yellow), .green(green));

    always #5 clk = ~clk;

    initial begin
        #12 rst = 0;
        #400 $finish;   // long enough to see multiple full RED->GREEN->YELLOW cycles
    end

    initial $monitor("t=%0t red=%b yellow=%b green=%b", $time, red, yellow, green);
endmodule

Project 3: Digital Lock — A Sequence-Detector FSM

Our digital lock unlocks only when it sees the exact bit sequence 1-0-1-1 arrive, one bit per clock cycle, on a single serial input line — a classic FSM pattern used in real password/protocol detection circuits.

digital_lock.v — detects serial pattern "1011"
module digital_lock (
    input  wire clk, rst, in,
    output reg  unlock
);
    localparam S0=3'd0, S1=3'd1, S2=3'd2, S3=3'd3, S4=3'd4;

    reg [2:0] state, next_state;

    // Block 1: state register
    always @(posedge clk or posedge rst) begin
        if (rst) state <= S0;
        else        state <= next_state;
    end

    // Block 2: next-state logic (combinational)
    always @(*) begin
        case (state)
            S0: next_state = in ? S1 : S0;
            S1: next_state = in ? S1 : S2;
            S2: next_state = in ? S3 : S0;
            S3: next_state = in ? S4 : S2;
            S4: next_state = in ? S1 : S0;   // unlocked -- restart detection right away
            default: next_state = S0;
        endcase
    end

    // Block 3: output decode
    always @(*) unlock = (state == S4);
endmodule
Notice: three always blocks, not two
This FSM splits state register, next-state logic, and output decode into three separate blocks — an even cleaner variation of the two-block pattern from the traffic light, and arguably the clearest possible way to write any FSM. Many professional style guides require exactly this three-block structure.
digital_lock_tb.v
module digital_lock_tb;
    reg clk = 0, rst = 1, in = 0;
    wire unlock;

    digital_lock uut (.clk(clk), .rst(rst), .in(in), .unlock(unlock));

    always #5 clk = ~clk;

    initial begin
        #12 rst = 0;

        // feed in 1,0,1,1 -> should unlock right after the final '1'
        in=1; #10; in=0; #10; in=1; #10; in=1; #10;
        $display("After 1011: unlock=%b (expect 1)", unlock);

        // feed in a wrong sequence, 1,1,0 -> should NOT unlock
        in=1; #10; in=1; #10; in=0; #10;
        $display("After 110: unlock=%b (expect 0)", unlock);

        $finish;
    end
endmodule

Common Mistakes in FSM Design

  • Forgetting the default case in next-state logic — an unreachable/undefined state can leave the FSM permanently stuck, since there's no rule for what happens next.
  • Mixing state-update and output logic in one always block — makes the FSM much harder to read, debug, and modify; always prefer the two/three-block separation shown here.
  • Choosing a DIVISOR/timer value impossible to simulate quickly — always parameterize timing constants so testbenches can use tiny values while real hardware uses realistic ones.
  • Forgetting that unlock is only HIGH for one clock cycle in this Moore-style design — a real lock mechanism would typically need to latch or extend that pulse for a human-usable duration.

Summary

The LED blinker demonstrates why real designs need clock dividers — human-visible timing requires counting down from a much faster hardware clock. The traffic light is a complete, real Finite State Machine, cleanly split into a state/timer register and a combinational output-decode block. The digital lock is a sequence-detector FSM, using the even cleaner three-block style (state register, next-state logic, output decode) to detect the pattern "1011" arriving one bit per clock cycle.

Interview Questions

  • Why can't an LED be directly toggled by a raw 50 MHz FPGA clock?
    50 MHz means the clock toggles 50 million times per second — far faster than the human eye can perceive, so the LED would appear constantly (dimly) lit rather than visibly blinking. A clock divider counts down to a much slower effective toggle rate.
  • Why is the two/three-always-block FSM style preferred over combining everything into one block?
    Separating state update (sequential), next-state logic, and output decode (combinational) keeps each block's responsibility singular and clear, making the design far easier to read, debug, and modify — and keeps blocking/non-blocking assignment usage consistent with Chapter 13's rules.
  • What happens to the digital_lock FSM if it receives an unexpected reset mid-sequence?
    Since rst is asynchronous, the FSM immediately returns to S0 regardless of the clock, discarding any partially-matched sequence — a deliberate, safe behavior for a lock circuit.

Viva Questions

  • In traffic_light.v, how many states does the FSM have?
    Three: RED, GREEN, YELLOW.
  • What sequence does digital_lock.v detect?
    1011, arriving one bit per clock cycle on the serial input `in`.
  • Why does led_blinker use a parameter for DIVISOR instead of a fixed number?
    So simulation can use a small, fast-to-test value while real hardware deployment can use a large, realistic value for a human-visible blink rate — without changing the module's code.
