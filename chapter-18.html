Encoder, Decoder & Priority Encoder

Full theory in Chapter 4. Here: a decoder with enable, a plain encoder (and exactly why it breaks with multiple active inputs), and a priority encoder that fixes that problem — written two different ways.

📖 Beginner Level🕐 —🧩 6 sections

Quick Recap (Full Theory in Chapter 4)

A decoder activates exactly one of 2ⁿ outputs based on an n-bit code. An encoder does the reverse — reporting the binary code of whichever single input is active. A priority encoder is a smarter encoder that behaves sensibly even when multiple inputs are active at once.

2-to-4 Decoder (with Enable)

decoder2to4.v
module decoder2to4 (
    input  wire [1:0] in,
    input  wire       en,
    output reg  [3:0] out
);
    always @(*) begin
        out = 4'b0000;         // default: nothing selected
        if (en) begin
            case (in)
                2'b00: out[0] = 1'b1;
                2'b01: out[1] = 1'b1;
                2'b10: out[2] = 1'b1;
                2'b11: out[3] = 1'b1;
            endcase
        end
    end
endmodule

The en (enable) input is standard practice on real decoders — when LOW, every output stays 0 regardless of in, letting several decoders share the same address lines while only one is "switched on" at a time (exactly how a memory chip selects which device responds to an address).

Plain 4-to-2 Encoder — And Exactly Why It Breaks

encoder4to2.v — assumes exactly one input is ever active
module encoder4to2 (
    input  wire [3:0] in,
    output reg  [1:0] out
);
    always @(*) begin
        case (in)
            4'b0001: out = 2'b00;
            4'b0010: out = 2'b01;
            4'b0100: out = 2'b10;
            4'b1000: out = 2'b11;
            default:    out = 2'b00;  // what SHOULD this mean? see below
        endcase
    end
endmodule
The problem, laid bare
This encoder only has one line per exact 4-bit pattern with a single 1. But real-world inputs are messy — what if in = 4'b0110 (two bits active) or in = 4'b0000 (none active)? Both fall into the same catch-all default, producing the exact same output (00) as if only in[0] were active — a completely wrong, silently misleading result. A plain encoder is only safe when you can guarantee exactly one input is ever active — which is rarely true in real systems.

The Fix: Priority Encoder

A priority encoder resolves the ambiguity by explicit rule: if multiple inputs are active, the highest-priority one (conventionally, the highest-indexed bit) wins, and it adds a valid output that's only HIGH when at least one input was actually active — directly solving the "was it really input 0, or was nothing active at all?" problem above.

Version 1: if/else Priority Chain (Chapter 11)

priority_encoder4to2.v
module priority_encoder4to2 (
    input  wire [3:0] in,
    output reg  [1:0] out,
    output reg       valid
);
    always @(*) begin
        valid = 1'b1;
        if (in[3])      out = 2'b11;   // in[3] checked FIRST: highest priority
        else if (in[2]) out = 2'b10;
        else if (in[1]) out = 2'b01;
        else if (in[0]) out = 2'b00;
        else begin
            out   = 2'b00;
            valid = 1'b0;      // nothing was active at all
        end
    end
endmodule

Version 2: casez With Don't-Care Wildcards (Chapter 3 + Chapter 11)

priority_encoder_casez.v — same behavior, wildcard style
module priority_encoder_casez (
    input  wire [3:0] in,
    output reg  [1:0] out
);
    always @(*) begin
        casez (in)              // ? = don't-care bit, matches 0 or 1
            4'b1???: out = 2'b11;   // in[3]=1, everything else irrelevant
            4'b01??: out = 2'b10;
            4'b001?: out = 2'b01;
            4'b0001: out = 2'b00;
            default: out = 2'b00;
        endcase
    end
endmodule

Both versions are functionally identical — casez simply expresses the exact same priority logic as a compact pattern list instead of a chain of conditions, using the don't-care ? wildcard exactly like a Karnaugh map's don't-care cells from Chapter 3.

Testbench — Proving the Priority Behavior

priority_encoder_tb.v
module priority_encoder_tb;
    reg [3:0] in;
    wire [1:0] out;
    wire       valid;

    priority_encoder4to2 uut (.in(in), .out(out), .valid(valid));

    initial begin
        in = 4'b0000; #10;   // expect valid=0 (nothing active)
        in = 4'b0001; #10;   // expect out=00, valid=1
        in = 4'b0110; #10;   // TWO bits active (1 and 2) -> expect out=10 (bit 2 wins)
        in = 4'b1111; #10;   // ALL bits active -> expect out=11 (bit 3 wins, top priority)
        $finish;
    end

    initial $monitor("t=%0t in=%b -> out=%b valid=%b", $time, in, out, valid);
endmodule

Common Mistakes

  • Using a plain encoder when multiple inputs can genuinely be active simultaneously — always confirm this assumption before choosing between plain and priority encoder.
  • Forgetting the valid output — without it, "no input active" and "input 0 active" are indistinguishable to whatever circuit reads the encoder's output.
  • Getting the priority direction backwards — always double check whether your specification wants the highest-indexed or lowest-indexed input to win.
  • Missing bits in a casez wildcard pattern (e.g., writing 01? for a 4-bit input instead of 01??) — pattern widths must always match the full input width.

Summary

A decoder activates exactly one output line matching an input code (often gated with an enable). A plain encoder assumes exactly one input is active and silently gives wrong answers otherwise. A priority encoder fixes this by explicitly defining which input wins when several are active, and adds a valid flag distinguishing "input 0 active" from "nothing active" — writable either as an if/else priority chain or, equivalently, using casez wildcards.

Interview Questions

  • Why does a plain encoder fail when multiple inputs are active?
    Because its case statement only has entries for the exact single-bit-active patterns; any other combination (multiple bits, or none) falls into the default case, producing an output indistinguishable from a legitimate single-input-active case — silently wrong.
  • What is the purpose of the valid output in a priority encoder?
    It distinguishes the case where input 0 is genuinely active from the case where no input is active at all — both of which would otherwise produce the same all-zero output code.
  • How does casez differ from a plain case statement here?
    casez allows `?` wildcard bits in its patterns, matching either 0 or 1 at that position, letting a priority encoder's logic be expressed as compact patterns instead of an explicit if/else chain — both produce identical hardware.

Viva Questions

  • In priority_encoder4to2, which input bit has the highest priority?
    in[3] — it's checked first in the if/else chain.
  • What does the ? symbol mean inside a casez pattern?
    A don't-care wildcard — it matches either 0 or 1 at that bit position.
